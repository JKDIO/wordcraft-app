## L39. ★★소스의 버전 상수를 안 올리면 "업데이트 있음"이 영구 오탐으로 남는다★★ (2026-08-14 제정, 노트북 동기화 중 발견)

- **문제**: v1.4.31 → v1.4.34까지 네 번 배포하면서 서버 `version.json`은 매번 올렸지만
  **소스의 `APP_VERSION` 상수는 `1.4.30`에 멈춰 있었다.** 배너 로직은
  `isNewer(서버.version, APP_VERSION)` 이다. 즉 **최신 번들을 받은 아이에게도 "새 버전이 있어요"가 계속 떠 있었다.**
  누르면 `location.reload()` → 아무것도 안 바뀜 → 또 뜸. 하단 정보 탭에는 빨간 `!` 가 상주.
  `정보` 화면의 버전 표기도 실제 1.4.34인데 **v1.4.30으로 보였다.**
- **왜 못 잡았나**: 세 번의 배포 모두 화면을 눈으로 봤다. 그런데 **본 화면이 장비창이었다.**
  버전 배너는 다른 화면에 있었고, 나는 그 화면을 열지 않았다.
  START_HERE의 "진실 3종 대조"도 **서류상 숫자만 맞춰 놓고 소스 상수를 실제로 열어보지 않았다.**
- **규칙**:
  1. **릴리스 체크리스트에 `app/src/lib/version.ts`의 `APP_VERSION`을 넣는다.** `version.json`만 올리는 배포는 미완이다.
  2. 진실 3종 대조는 *"문서에 적힌 숫자가 같은가"* 가 아니라 **"세 곳(릴리스 노트·라이브 version.json·소스 상수)을 실제로 열어서 읽었는가"** 다.
  3. 오탐 알림은 기능 결함보다 나쁘다. **아이가 경고를 무시하도록 훈련시킨다.** 다음에 진짜 업데이트가 와도 안 누른다.
- **조치·검증**: `APP_VERSION='1.4.34'` 커밋 `d65b4fd` → CI 재빌드(main.js sha256 `021ef9bf…`→`cde284c2…`)
  → 라이브 `#/info` 에서 "현재 v1.4.34 / 최신 v1.4.34 · ✓ 최신 버전을 쓰고 있어요" 및 빨간 `!` 소멸 확인(PC 브라우저). 실기기 미확인.
- **연결**: L22(들리지 않는 음원)·L36(로컬은 맞고 배포본만 깨짐)·L38(CDN 캐시)과 **같은 실패 모양** —
  "내가 확인한 것"과 "아이가 실제로 겪는 것"이 다른 경로였다.

## L40. ★★컨테이너 작업본은 SSOT가 아니다 — 스냅샷은 GitHub에서 뜨고 해시로 증명한다★★ (2026-08-14 제정)

- **실측**: 이 세션 끝에 컨테이너 `/home/claude/wc` 와 GitHub `app/` 를 전수 대조했더니
  **57개 중 14개가 어긋나 있었다.** `src/lib/review.ts` 는 컨테이너에 **아예 없었다**(GitHub에만 존재).
  세션을 거듭하며 GitHub에 직접 넣은 수정이 컨테이너로 돌아오지 않은 탓이다.
  **이 상태로 컨테이너를 노트북에 복사했다면 기능 14개를 되돌리는 사고였다** (L11이 경고한 바로 그것).
- **방법 (토큰 거의 안 든다)**:
  1. GitHub 디렉터리 목록 조회 → 각 파일의 `sha` 는 **git blob SHA-1** 이다.
  2. 노트북·컨테이너에서 `git hash-object <파일>` (저장소가 아니어도 동작).
  3. 두 목록을 비교 → **다른 것만** 옮긴다. 파일 내용은 대부분 문맥을 통과할 필요조차 없다.
  4. 옮긴 뒤 **목적지에서 다시 `git hash-object` 로 대조** — 일치하면 한 글자도 안 틀렸다는 증명이다(L36 봉인).
- **규칙**: 노트북 스냅샷 `src_v<버전>/` 은 **직전 스냅샷을 복사한 뒤 델타만 덮어쓰고, 전 파일 해시를 GitHub와 대조**해서 만든다.
  컨테이너 작업본은 초안일 뿐이다.

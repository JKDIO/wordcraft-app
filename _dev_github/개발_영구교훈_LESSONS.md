## L0. ★진짜 근본 원인★ — 컨테이너에서 대용량 배포 = 토큰 funnel
- 이 컨테이너는 Vercel/Supabase 직접 접속 차단(HTTP 000), npm 레지스트리도 차단(HTTP 403), **GitHub도 403(host_not_allowed)**. 그래서 배포 파일(수백 KB~1MB)의 **모든 바이트가 모델 문맥을 통과**해야 하고, 이게 배포 1회당 ~20만+ 토큰을 태운다.
- "앱이 무거워서"가 아니다. 앱은 gzip 78KB로 매우 가볍다. **"컨테이너에서 배포"라는 방식이 구조적으로 비싼 것.**
- **해결: 배포는 네트워크가 되는 곳에서 한다 — (a) 사용자 PC에서 `vercel deploy` 또는 vercel.com 드래그드롭, (b) GitHub 연동 push=자동배포, (c) 정적 자산은 APK에 오프라인 번들해 배포 자체를 제거.**
- 컨테이너 relay(tar→base64→Supabase→Vercel fetch)는 자산이 모델 문맥을 통과하므로 여전히 비싸다. 최후의 수단.
- 보완(7/15 확인): 컨테이너 빌드 산출물은 SendUserFile→device_commit_files로 모델 문맥 없이 노트북에 전달 가능. GitHub 업로드 페이지에 사용자가 드래그(2분) → 자동배포. 이 조합이 현재 최적 경로.
- 추가(7/15 저녁): react/react-dom/typescript는 컨테이너 `/home/claude/.npm-global/lib/node_modules`에 **이미 글로벌 설치돼 있다** (react 19, 2026-07-23 세션은 19.2.6). npm 403이어도 빌드 가능 — node_modules 심링크만 걸면 됨. 대량 파일 스테이징은 폴더 연결 후 device_stage_files(문맥 무통과)가 정답.
- 추가(7/15 밤): **Vercel MCP `deploy_to_vercel`은 컨테이너에서도 작동한다** (MCP 프록시 경유) — 작은 정적 배포(리다이렉트 페이지 등)는 이걸로 즉시 가능. 단, 본 앱(wordcraft-app)은 GitHub 연동 파이프라인 유지(이중 배포 경로 금지). 기존 프로젝트에 배포 시 저장돼 있던 buildCommand가 그대로 실행되니 projectSettings를 명시할 것.
- 추가(7/16): 크롬 확장(claude-in-chrome)의 file_upload는 노트북 로컬 파일·Cowork 연결 폴더를 첨부하지 못한다(세션 공유 파일만 허용). **보강(8/1 확인): 컨테이너의 `/mnt/user-data/outputs/`에 둔 파일은 file_upload로 첨부된다 — 즉 빌드 산출물을 outputs로 복사하면 GitHub 업로드까지 클로드가 100% 자동으로 끝낼 수 있다(v1.4.15에서 3파일 업로드·커밋 검증).** 커밋 버튼 위치는 ProTip 문구 출현으로 밀리니 클릭 후 스크린샷 확인.
- **추가(7/23): 저장소 다운로드는 브라우저로 직접 가능** — claude-in-chrome으로 `codeload.github.com/<owner>/<repo>/zip/refs/heads/main` 내비게이션 → Downloads 저장 → Downloads 폴더 접근 승인 → device_bash `unzip`으로 연결 폴더에 복원(컨테이너 GitHub 403 우회). 파일을 컨테이너로 가져올 땐 device_stage_files(문맥 무통과).

## L13. ★START_HERE는 삭제가 아니라 자가검증 + 세션 종료 갱신★ (Dio님 지적 2026-07-15)
- 우려: "현재 상태" 스냅샷 문서는 몇 세션 지나면 낡아 다음 세션을 오도할 수 있다. **하지만 삭제는 더 위험**(진입점·불변 규칙까지 소실).
- 해결: **낡지 않는 진실 3종** — ① RELEASE_LOG(append-only, 맨 위=최신) ② 라이브 `/version.json` ③ 소스 `APP_VERSION`. START_HERE는 "지도 + 마지막 스냅샷"이며 상단에 **버전 스탬프**를 둔다.
- **세션 시작**: 스탬프 == RELEASE_LOG 맨 위 == 라이브 version.json == 소스 APP_VERSION 자가검증. 어긋나면 START_HERE가 낡은 것 → 세 진실 신뢰 + START_HERE 갱신(삭제 금지).
- **세션 종료**: 코드/배포 변경 시 RELEASE_LOG 항목 추가 + START_HERE 스탬프·다음작업 갱신을 **의무**로 한다.
- 주의(7/16): 라이브 version.json을 WebFetch로 확인할 땐 **캐시 주의** — 반드시 캐시버스터 쿼리(`?cb=...`)를 붙일 것.

## L16. ★배포 전 번들 스모크 테스트 의무 + bun은 `--production` 명시★ (2026-07-16 오전, v1.2.2 배포사고로 제정)
- **사고**: v1.2.2 1차 배포 main.js가 라이브에서 화면 백지(TypeError: U is not a function). tsc·빌드·파일 크기 정상이었지만 **런타임 즉사** — bun이 `NODE_ENV=production`만으로는 JSX를 production 런타임으로 전환하지 않아 jsxDEV로 컴파일했고, react production 번들에선 jsxDEV가 undefined. 세션마다 컨테이너 bun 버전이 달라 어제 되던 명령이 오늘 깨진다.
- **규칙**: ① 컨테이너 bun 빌드는 **반드시 `bun build --production`**. ② **배포 전 번들 스모크 테스트 의무**: playwright+chromium 프리인스톨(`/opt/pw-browsers/chromium`) — 빌드 산출물을 로컬 http로 서빙해 핵심 화면이 JS 에러 없이 렌더되는지 확인한 뒤에만 배포. ③ 마커 grep은 렌더 테스트를 **대체하지 못한다**. ④ 배포 후 라이브 검증은 version.json만이 아니라 **실제 화면 렌더**까지.
- 보강(7/16 밤, v1.4.1): 오디오처럼 렌더만으로 못 잡는 버그는 **계측 스모크**로 — HTMLMediaElement.play/speechSynthesis.speak를 후킹해 호출 횟수를 세고, 외부 오디오 URL은 page.route로 로컬 mp3를 주입해 "클립 성공" 상황을 재현한다. ⚠️(8/1 추가) page.route는 **나중에 등록한 것이 먼저 매칭**된다 — 포괄 패턴을 먼저, 구체 패턴(스토리지 mp3)을 나중에 등록해야 한다(순서 뒤집으면 mp3가 JSON으로 채워져 "전부 폴백" 오판을 낳는다).
- **보강(7/18, v1.4.5/v1.4.6)**: 이 컨테이너의 playwright chromium은 **supabase.co로 나가는 네트워크가 막혀** 있어 원격 클립을 실제로 재생하지 못한다 — 로컬 계측 스모크는 **코드 경로만** 증명한다. **클립이 실제로 소리 나는지는 반드시 라이브(사용자 실제 Chrome, claude-in-chrome)에서** 확인할 것.

## L33. ★★대용량 바이너리는 내가 옮기지 않는다 — 서버가 가져가게 하라★★ (2026-08-14, 기사 스프라이트 작업으로 제정)

- **문제**: fal.ai로 생성한 이미지를 앱에 넣어야 하는데, **이 환경에서 이미지 바이트를 옮길 통로가 전부 막혀 있었다.** 하나씩 실측한 결과:

  | 시도 | 결과 |
  |---|---|
  | 컨테이너 → fal CDN `curl` | 프록시 403 |
  | 브라우저 JS `fetch` / `XHR` | 전면 차단 |
  | 브라우저 다운로드(`<a download>`) | 클릭 권한이 보기 전용 → user gesture 생성 불가 |
  | JS 결과로 base64 반환 | 툴이 차단 |
  | 데스크톱 VM(`device_bash`) | 네트워크 없음 |
  | 이미지 문서(image document) 페이지 | CSP가 `fetch`·`data:` 전부 거부 |

- **해답**: 바이트를 **내 쪽으로 가져오려 하지 말고, 네트워크가 되는 서버가 직접 가져가게** 한다.
  ```
  fal URL ──▶ Postgres(pg_net) ──▶ Edge Function art-forge ──▶ Supabase Storage
                                    └ 서버가 fal에서 직접 fetch → 후처리 → 저장
  ```
  SQL 한 줄이 비용의 전부다. **이미지가 모델 문맥을 한 번도 통과하지 않는다.**
- **규칙**:
  1. 외부에서 받아 어딘가에 넣어야 하는 대용량 자산은 **Edge Function + `pg_net`** 으로 처리한다. 통로를 뚫으려 애쓰지 말고 통로가 필요 없는 구조로 바꾼다.
  2. 결과 확인은 **공개 URL을 브라우저에서 `<img>`로 띄우고 스크린샷**으로 한다.
  3. ★**canvas 엘리먼트는 CDP 스크린샷에 합성되지 않는다.**★ 반드시 `toDataURL()` → `<img>` 로 바꿔서 봐야 한다.
  4. 브라우저 작업대는 **CSP가 느슨한 일반 페이지**(예: `example.com`)를 쓴다. 이미지 문서 위에서는 `fetch`도 `data:`도 안 된다.
  5. 크로스 오리진 이미지는 `<img crossOrigin="anonymous">` 로 불러오면 canvas가 오염되지 않는다(fal.media·Supabase Storage 모두 CORS 허용 확인).
- **일반형**: L0·L7이 "대용량을 문맥에 통과시키지 마라"였다면, 이것은 **"통과시킬 필요가 없도록 일을 서버로 옮겨라"** 이다.

## L34. ★★큰 파일을 통째로 다시 쓰지 않아도 되게 구조를 만들어라★★ (2026-08-14, 배포 자동화로 제정)

- **문제**: 저장소의 `main.js` 460KB · `app.css` 114KB · `RELEASE_LOG.md` 150KB · `LESSONS.md` 52KB.
  다섯 줄을 고치려고 이 파일들을 통째로 커밋하면 **바이트 전부가 모델 문맥을 통과**한다(L7). 그래서 지금까지 배포를 사람 손(브라우저 드래그)에 맡겨 왔다.
- **해답 — 세 가지 장치**:
  1. **번들은 CI가 만든다.** 소스를 `app/` 에 두고, 작은 소스 파일만 커밋하면 GitHub Actions(`wc-build`)가 빌드해 루트 `main.js`·`app.css`를 갱신한다 → Vercel 자동 배포. 소스 트리 자체도 저장소에 이미 있는 tgz를 **CI가 풀어서**(`wc-bootstrap`) 만들었다 — 토큰 0.
  2. **CSS는 조각으로 넣는다.** `public/css.d/NN-이름.css` 를 빌드가 `app.css` 뒤에 이어 붙인다. 큰 CSS를 다시 쓰지 않는다.
  3. **append-only 문서는 파일을 나눈다.** 릴리스 노트는 `_dev_github/RELEASE_v1.4.31.md` 처럼 릴리스마다 한 파일. 이 교훈 문서도 2권으로 나눴다.
- **CI는 결과를 작은 파일로 되돌려 보고한다**: `_ci/BUILD_REPORT.txt`(번들 크기·sha256·gzip), `_ci/BOOTSTRAP_REPORT.txt`(파일 목록). **460KB를 읽지 않고도 빌드가 옳게 됐는지 확인**할 수 있다.
- **안전장치**: 번들이 300KB 미만이면 CI가 실패한다. 깨진 빌드가 예한이가 쓰는 라이브 앱을 덮어쓰면 안 된다(L16의 자동화판).
- **규칙**:
  1. 파일이 50KB를 넘어가면 **"이 파일을 다음에 고칠 때 얼마가 드는가"** 를 먼저 계산한다. 비싸면 구조를 바꾼다.
  2. 무거운 일은 **CI에게 시킨다.** 내가 하는 일은 작은 방아쇠 파일을 미는 것뿐이어야 한다.
  3. 자동화에는 반드시 **되돌아오는 보고서**를 붙인다. 결과를 못 보는 자동화는 신뢰할 수 없다.
- **주의 — GitHub Fine-grained 토큰의 함정**: Repository access를 **`Public repositories`** 로 두면 **공개 저장소 읽기 전용**이고, 그 상태에서는 `Repository permissions` 칸 자체가 화면에 나타나지 않는다. 쓰기가 필요하면 **`All repositories`**(또는 select) + **Contents = Read and write** + **Workflows = Read and write**(워크플로 파일을 만들려면 별도로 필요). `Administration`은 끈다.

## L35. ★부위별 성장 UI는 "그림"이 아니라 "레이어"로 만든다★ (2026-08-14, 룬 장비창 v1.4.31로 제정)

- **지적(Dio님)**: *"흉갑, 검, 망토, 귀걸이, 오라 등등 있는데 하나도 안 보여."* v1.4.28의 장비창은 12×16 픽셀에 팔레트만 갈아끼웠다. 슬롯 이름은 11개인데 화면엔 옷 색만 변했다 — **UI가 아니라 거짓말이었다.**
- **첫 시도의 실패**: 도형 코드로 전신을 그렸더니(64×88) 흉갑이 팔을 삼키고 검·어깨·망토·왕관이 겹쳐 최고 등급이 형체 없는 덩어리가 됐다. 원인은 그림 실력이 아니라 **공간 배분**이었다.
- **해답**: 베이스 몸 1장 + **부위 레이어 44장(11슬롯 × 4등급)** 을 `<img>` 로 겹친다.
  - 레이어를 뽑는 방법: 생성 모델에 "이 몸에 투구를 씌워라"라고 하면 **몸을 픽셀 단위로 보존**한다. 그래서 **베이스와 diff를 뜨면 정렬이 보장된 장비 레이어**가 나온다. "장비만 그리고 몸은 지워라"라고 하면 모델이 몸을 안 지운다 — **지우라고 하지 말고 diff로 뽑아라.**
  - 커리큘럼이 늘어 뱃지가 100개가 되어도 **그림은 다시 안 그린다.** 슬롯의 분모만 바뀐다(L30의 시각판).
- **규칙**:
  1. 성장하는 캐릭터 UI는 **부위 레이어 + z-order**로 설계한다. 등급마다 전신을 새로 그리면 유지가 불가능하다.
  2. **z-order를 규격에 못 박는다.** 무기는 투구보다 뒤에 그려야 한다 — 앞에 두면 투구 장식이 검을 덮는다(실제로 발생, Dio님 지적).
  3. **얼굴은 어느 등급에서도 가리지 않는다.** 아이가 자기 얼굴을 봐야 애착이 생긴다. 생성 프롬프트의 negative에 `closed helmet hiding the face`를 넣는다.
  4. **이펙트·날개·망토는 프레임 가장자리에서 여백을 남긴다.** 가장자리에 닿으면 배경 제거가 실패해 사각형 덩어리가 남는다.
  5. **최고 등급은 반드시 따로 검수한다.** 모든 슬롯이 켜진 상태는 색이 많아 팔레트 감축에서 뭉개진다(36색 → 56색으로 올려 해결). 그리고 번잡해진다 — 장식·파티클은 절제한다(Dio님 지적).
  6. **폴백을 남긴다.** 이미지 로드 실패(비행기모드·CDN 장애) 시 옛 픽셀 영웅으로 물러난다. 보상 화면이 빈 칸이 되면 안 된다.
- **한계(정직하게)**: 슬롯 등급이 4단계라 **뱃지 하나하나가 전부 그림을 바꾸지는 않는다**(1/3·2/3·전부 지점에서 바뀐다). 숫자는 뱃지마다 즉시 오른다. 예한이 실기기 확인은 아직 못 했다.

## L36. ★한글은 손으로 이스케이프하지 마라 — 한 글자가 틀리면 아이 화면에 그대로 나간다★ (2026-08-14, '뭃지' 사고로 제정)

- **사고**: 장비창 안내문이 라이브에서 **"그 분야 뭃지로 바로 간다"** 로 나갔다. Dio님이 물었다 — *"뭃지가 뭐야 도대체?"*
- **원인**: 소스를 GitHub API로 올릴 때 한글을 유니코드 이스케이프로 손수 적었고, `뱃`(U+BC43)을 `뭃`(U+BB43)으로 **한 자리 틀렸다.** 로컬 소스는 처음부터 정상이었다 — **전송 과정에서만 깨졌다.**
- **왜 안 걸렸나**: 타입검사도 빌드도 통과한다(둘 다 유효한 한글이다). 로컬 파일을 grep해도 정상이다. **로컬과 배포본이 다르다는 것을 아무도 확인하지 않았다.**
- **규칙**:
  1. **한글·이모지는 이스케이프하지 않고 UTF-8 그대로 보낸다.** 도구가 받아준다. 손으로 코드포인트를 쓰는 순간 오타는 시간문제다.
  2. **배포 후 화면 문구를 실제로 읽어라.** 버전 문자열 대조(L25)는 코드가 맞다는 뜻이지 **글자가 맞다는 뜻이 아니다.** 아이에게 보이는 문장은 눈으로 읽는다.
  3. 자동 검사에 넣는다면: 배포본에서 한글 문자열을 뽑아 **로컬 소스의 같은 문자열과 대조**한다. 다르면 실패.
- **일반형**: 이 프로젝트에서 반복되는 형태다 — **"통과했다"는 검사가 실제 결함과 다른 것을 보고 있었다**(L22 파형·L26 입력방식·L29 커버리지). 검사 대상이 사용자가 겪는 것과 같은지 매번 물어라. 아이가 읽는 것은 타입이 아니라 글자다.

*이 파일은 append-only. 새 교훈은 여기 끝에 L번호를 붙여 추가한다.*


## L37. ★위치는 "왼손/오른손"이 아니라 "화면의 어느 쪽"으로 지정한다★ (2026-08-14, 곡괭이-검 겹침으로 제정)

- **사고**: 예한이 캐릭터가 곡괭이와 검을 **같은 쪽에 겹쳐 들고** 있었다. Dio님: *"곡괭이는 오른손에 있어야 하는 거 아냐? 칼이랑 겹쳐 있는데?"*
- **원인**: 44개 레이어를 생성할 때 `held in his LEFT hand (the viewer's right)` 라고 썼다. 모델은 이걸 **등급마다 다르게 해석**했다 — 2·4등급은 화면 왼쪽에, 1·3등급은 화면 오른쪽에 그렸다. 검은 전부 오른쪽이라 1·3등급에서 겹쳤다.
- **왜 안 걸렸나**: 레이어를 **하나씩** 검수했기 때문이다. 곡괭이만 놓고 보면 멀쩡하다. **겹침은 조합해야만 보인다.**
- **규칙**:
  1. 생성 프롬프트의 위치 지정은 **화면 기준**으로 한다 — `must sit entirely in the LEFT HALF of the image` / `the RIGHT HALF must remain completely empty`. "왼손"은 정면/후면·거울상에 따라 뜻이 달라져 모델이 흔들린다.
  2. **레이어는 반드시 조합해서 검수한다.** 부위별 단독 검수는 필요조건일 뿐이다. 같은 공간을 쓰는 부위끼리(양손 무기·망토와 날개·투구와 왕관) 조합 시트를 만들어 본다.
  3. 조합 검수는 **전 등급 × 전 조합**으로. 이번엔 2·4등급만 우연히 맞아서 "된다"고 착각했다.
- **부수 확인(좋은 소식)**: 자산이 앱 번들이 아니라 Storage에 있어서 **재배포 없이 즉시 고쳐졌다.** 이미지 결함은 SQL 두 번으로 끝난다 — 이게 L33 구조의 실질적 이득이다.

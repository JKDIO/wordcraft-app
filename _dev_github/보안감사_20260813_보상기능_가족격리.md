# 보안 감사 — 보상 기능의 가족별 격리 (2026-08-13)

> **성격**: 앱 배포 없음. **DB 정책(RLS)만 변경**했다. 데이터는 한 줄도 지우거나 바꾸지 않았다.
> **계기**: Dio님 지시 — "새로운 보상 기능(자녀/부모 앱 모두)은 각 가족별로 따로 진행되어야 하는 거 알고 있지? 완전무결하게. 기존 데이터는 보존."
> **관련 릴리스**: v1.4.22(보상 로드맵) · v1.4.23 — **다른 세션이 만든 기능이다.** 이 문서는 그 기능의 격리를 감사한 결과다.

---

## 0. 먼저 — 동시 작업 충돌을 피했다

이 세션의 컨테이너 소스는 **v1.4.21**이었는데, 확인해 보니 라이브는 **v1.4.22**, 노트북은 **v1.4.23**까지 진행돼 있었다(다른 세션 작업).
**여기서 빌드해 배포했다면 v1.4.22·v1.4.23을 통째로 날렸다.** L27이 경고하는 바로 그 사고다 — 그래서 **배포하지 않았고**, 앱 코드는 한 줄도 건드리지 않았다.

> 규칙 추가: **배포 직전 반드시 라이브 `version.json`과 내 소스 `APP_VERSION`을 비교한다.**
> 내 소스가 라이브보다 **낮으면** 그 컨테이너는 낡은 것이다 — 배포하지 말고 최신 소스를 먼저 확보한다.

---

## 1. 감사 방법

실제 데이터를 건드리지 않고, 트랜잭션 안에서 특정 사용자로 **가장(impersonate)** 해 RLS가 실제로 어떻게 동작하는지 실행해 보고 전부 롤백했다.

```sql
begin;
set local role authenticated;
set local request.jwt.claims = '{"sub":"<가장할 user_id>","role":"authenticated"}';
-- ... 읽기/쓰기 시도 ...
rollback;   -- 실제 데이터 무변경
```

진영이네에는 아직 보호자 계정이 없어서(guardians=0), 테스트용 보호자 멤버십을 트랜잭션 안에서 임시로 만들고 롤백했다.

---

## 2. 결과 ① 가족 **간** 격리 — 완벽했다

진영이네 보호자로 가장한 상태에서:

| 대상 | 결과 |
|---|---|
| 예한이의 보상 목표 | **0건** |
| 예한이의 마일스톤 지급 이력(parent_rewards) | **0건** |
| 예한이의 뱃지 | **0건** |
| 예한이의 학습 기록(answer_events) | **0건** |
| 보이는 learner | 찬영, 호영 (자기 가족만) |
| 남의 아이에게 보상 목표 심기 | **차단** |
| 남의 아이 보상 목표 변조 | **차단** |

→ `wc_my_learner_ids()` 기반 정책이 모든 보상 테이블에 걸려 있어 **가족 경계는 새지 않는다.**

## 3. 결과 ② 가족 **안** — 구멍이 있었다 (수정함)

예한이 **기기(익명 device 계정)** 로 가장한 결과, 수정 전에는:

| 시도 | 수정 전 | 수정 후 |
|---|---|---|
| 자기 보상 목표를 **새로 만들기** ("1 XP에 닌텐도") | **가능** | 차단 |
| 아빠가 만든 목표를 **스스로 "받았음" 처리** | **가능** | 차단 |
| 아빠가 만든 목표를 **삭제** | **가능** | 차단 |
| 마일스톤 지급 이력을 **스스로 기록** | **가능** | 차단 |
| 자기 목표 **읽기** (아이 앱에 필요) | 가능 | **가능(유지)** |

> 보상은 "아빠가 정하고 아이가 본다"가 전부인 기능이다. 아이가 목표를 만들거나 지울 수 있으면 **그 약속의 의미 자체가 사라진다.**
> 화면에는 그런 버튼이 없었지만, **RLS는 화면이 아니라 계정을 본다.** 앱 UI에 없다는 것은 방어가 아니다.

## 4. 적용한 변경 (마이그레이션 `reward_writes_guardian_only`)

```sql
-- 새 헬퍼: 그 아이의 가족에 owner/guardian 멤버십이 있는 사용자인가
create or replace function public.wc_is_guardian_of(p_learner uuid) returns boolean
language sql stable security definer set search_path to 'public' as $$
  select public.wc_is_owner() or exists(
    select 1 from public.memberships m
    join public.learners l on l.family_id = m.family_id
    where m.user_id = auth.uid() and m.role in ('owner','guardian') and l.id = p_learner)
$$;

-- reward_goals: INSERT/UPDATE/DELETE → 보호자 전용 (SELECT는 그대로 — 아이가 읽어야 한다)
-- parent_rewards: INSERT/UPDATE → 보호자 전용 (SELECT는 그대로)
```

- **무손실**: 정책 교체만. `drop policy` → `create policy`. 행 삭제·수정 없음.
- **앱 영향 0**: 아이 앱(`RewardBoard.tsx`)은 `db.select`로 **읽기만** 한다. 쓰기는 관제실(`AdminPage`)만 하고, 관제실은 보호자(구글) 계정으로 연다(Dio님 확인, 2026-08-13).
- **되돌리기**: 정책을 이전 `learner_id IN (wc_my_learner_ids())` 형태로 다시 만들면 즉시 원복된다.

### 적용 후 실측 (전부 통과)

| 주체 | 읽기 | 목표 생성 | 지급 처리 | 삭제 | 마일스톤 기록 |
|---|---|---|---|---|---|
| 예한이 기기(device) | ✅ 유지 | 차단 | 차단 | 차단 | 차단 |
| 아빠(보호자·owner) | ✅ | 가능 | 가능 | 가능 | 가능 |
| 진영이네 보호자 | 0건 | 차단 | — | — | — |

### 데이터 보존 확인 (적용 직후)

`reward_goals` 2 · `parent_rewards` 17 · `badges` 16 · `answer_events` 2,877 · `module_progress` 33 · `review_cards` 512 · `xp_events` 2,624 · `memberships` 19 — **감사 전과 동일**.

## 5. 남은 권고 (이번에 손대지 않음)

1. **`badges` 쓰기는 아이 기기가 한다** (`learner_id = wc_device_learner()`). 앱이 스스로 뱃지를 지급하는 구조라 의도된 것이지만, 원리상 아이 기기가 임의의 `badge_id`를 넣을 수 있다. 보상이 XP·목표에 걸려 있고 뱃지는 표시용이라 지금은 실익이 낮아 두었다.
2. **`wc_owners`·`tts_samples`에 RLS는 켜져 있는데 정책이 없다**(전면 차단 상태). 의도된 것으로 보이나 확인 필요.
3. **진영이네는 아직 보호자 계정이 0명**이다. 부모가 한 번도 로그인하지 않았다 — 초대 재발송 필요. 보호자가 없으면 그 집은 보상을 만들 수도 없다.
4. Supabase 어드바이저의 `anon_security_definer_function_executable` 경고들 — 대부분 내부에서 권한을 다시 검사하는 함수라 즉시 위험은 아니지만, `wc_admin_*` 계열은 `wc_is_owner()`로 막혀 있는지 한 번 더 확인할 가치가 있다.

---

## 6. 교훈 (L29 후보)

> **RLS는 화면이 아니라 계정을 본다.**
> "앱에 그런 버튼이 없다"는 방어가 아니다. 새 테이블을 만들 때 **읽는 주체와 쓰는 주체를 따로 적고**, 쓰기 권한은 실제로 쓰는 쪽에만 준다.
> 그리고 그것을 **가장(impersonate) 테스트로 실증**한다 — 정책을 눈으로 읽어서는 이런 구멍이 안 보인다. 이번 구멍도 정책 문장은 멀쩡해 보였다(`learner_id IN (내 아이들)`). 아이 기기도 "내 아이들"에 포함된다는 게 함정이었다.
